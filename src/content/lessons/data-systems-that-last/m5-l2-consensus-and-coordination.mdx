## Getting Nodes to Agree

**Consensus** means getting several nodes to agree on a value, such that:

- **Uniform agreement:** no two nodes decide differently.
- **Integrity:** no node decides twice.
- **Validity:** the decided value was actually proposed by someone.
- **Termination:** every node that doesn't crash eventually decides.

Termination is the hard part. A famous result (the FLP impossibility result) shows that in a fully asynchronous model where a node may crash, no deterministic algorithm can always guarantee termination. Practical algorithms escape this by using **timeouts** to suspect failures: they stay safe always, and make progress whenever the network behaves reasonably.

## Two-Phase Commit: Atomic, but Not Consensus

Before looking at real consensus, consider the protocol many people first meet: **two-phase commit (2PC)**, used to commit a transaction atomically across several databases or partitions.

1. **Prepare:** the coordinator asks every participant, "Can you commit?" Each participant makes sure it **can** commit no matter what (writes data durably, checks constraints) and votes yes or no.
2. **Commit or abort:** if all vote yes, the coordinator records its decision durably and tells everyone to commit; otherwise, abort.

The crucial weakness: once a participant has voted yes, it **must wait** for the coordinator's decision. If the coordinator crashes at that moment, participants are stuck **in doubt**, holding locks, possibly for a long time. 2PC is **blocking**.

<Pitfall title="Reaching for Distributed Transactions by Default">

**Common mistake:** using 2PC across microservices to keep their databases in sync.

It couples the availability of every service to the slowest and least reliable one, and a coordinator failure can lock up data across the system. Often a better design is a single source of truth plus **asynchronous, idempotent propagation** of changes, covered in Module 6.

</Pitfall>

## How Raft Works (Simplified)

Raft is a consensus algorithm designed to be understandable. Paxos, Zab (used by ZooKeeper), and Viewstamped Replication are close relatives. Raft's job is to keep a **replicated log** identical on a cluster of nodes, usually three or five.

  steps={[
    { title: "Term", subtitle: "a numbered epoch" },
    { title: "Election", subtitle: "majority vote" },
    { title: "Replicate", subtitle: "leader appends entries" },
    { title: "Commit", subtitle: "majority has stored it" },
  ]}
/>

1. **Terms.** Time is divided into numbered **terms**. Each term has at most one leader.
2. **Elections.** If a follower hears nothing from a leader within a randomized timeout, it becomes a **candidate**, increments the term, and asks for votes. A node votes for at most one candidate per term, and only for a candidate whose log is at least as up to date as its own. A candidate with votes from a **majority** becomes leader.
3. **Log replication.** Clients send commands to the leader, which appends them to its log and sends them to followers.
4. **Commit.** Once a **majority** has stored an entry, it's committed; the leader applies it and tells followers to apply it.
5. **Stale leaders are harmless.** If an old leader returns from a pause, any message it sends carries an older term number, and nodes reject it. This is the same idea as a fencing token.

Why majorities? Any two majorities overlap in at least one node, so a new leader's majority always includes someone who has every committed entry. With five nodes, the cluster tolerates two failures. With three, it tolerates one.

Costs: every write needs a majority round trip; a cluster can't make progress without a majority; and frequent elections, caused by timeouts that are too aggressive or by network trouble, hurt availability.

## Coordination Services

Most applications don't implement consensus themselves. They use a **coordination service** built on it, such as **etcd** (Raft) or **ZooKeeper** (Zab). These hold small amounts of critical data in memory, replicated by consensus, and offer:

- **Linearizable key-value operations** and compare-and-set.
- **Leases and locks**, with fencing via increasing version or transaction numbers.
- **Leader election** for other systems.
- **Membership and failure detection:** which nodes are alive.
- **Change notifications:** clients can watch keys and react.

Typical uses: deciding which node is the leader of each partition, storing partition maps (Lesson 3.2), and holding cluster configuration. Kubernetes stores its cluster state in etcd, for example.

Keep these services for **slow-changing coordination data**, not application data. They're built for correctness, not throughput.
