## "The Agent Wrote It" Is Not an Answer

When a bug reaches production, nobody asks which tool typed the line. They ask who reviewed it, who approved it, and who can fix it. Foundations called this **deployment diligence**: taking responsibility for AI-assisted work once it leaves your hands.

With an agent, that responsibility is easy to lose track of, because so much of the work happened while you weren't watching. This lesson is about keeping it.

---

## The Explain-It Test

Before you commit agent-written code, ask yourself:

> Could I explain this change, line by line, to a reviewer, and defend each decision without asking the agent?

If yes, it's your code. If no, you have three honest options: learn it until you can (ask the agent to walk you through it), cut it down to what you understand, or mark it clearly for a reviewer who does understand it.

The test scales with risk. A generated test fixture doesn't need line-by-line mastery. An authorization check does.

## Disclosure: Say What Matters

Norms differ by team, employer, open-source project, and school. What doesn't vary: **don't misrepresent how the work was made when it matters to the people relying on it.**

| Context | Common practice |
|---|---|
| Your team's repo | Follow team policy. Many teams use a `Co-Authored-By` trailer or a PR note for substantial agent contributions. |
| Open-source projects | Read `CONTRIBUTING.md`. Some projects require disclosure; some don't accept AI-generated contributions at all. |
| Coursework and assessments | Follow the course's AI policy exactly. When in doubt, disclose and ask. |
| Client work | Check the contract and your organization's rules on AI tools and client code. |
| Security fixes and incident work | Note what was AI-assisted in the write-up, so later reviewers know what to double-check. |

Claude Code can add attribution to commits and pull requests it creates. Whether to keep it is a decision for you and your team, but make it on purpose.

<Pitfall title="Rubber-Stamp Review of Agent PRs">

**Common mistake:** a teammate opens a 1,200-line agent-written pull request, and the reviewer approves it after a skim because "the AI already checked it."

Now nobody has really reviewed it: the author trusted the agent, and the reviewer trusted the author. Teams that use agents well keep pull requests small, require the author to have read every line first, and ask for a short human-written note on *why* the change is right, not just *what* changed.

</Pitfall>

If you lead a team, agree on these together. The [AI Fluency for Leaders & Teams](/courses/ai-fluency-leaders-teams/) course covers the policy side.

- **A shared, committed CLAUDE.md and settings file**, reviewed like code.
- **Agreed permission defaults** per repo: which modes are fine, which commands are always denied.
- **A size limit for pull requests**, agent-assisted or not.
- **Clear lines for "human decides"**: architecture, security, data handling, dependency additions.
- **A way to share what works**: useful slash commands, skills, and briefs, plus a short log of agent mistakes and the fixes the team added.

## Keep Your Own Skills Sharp

The last kind of diligence is toward yourself. If the agent always debugs, you stop learning to debug. That's fine for some skills and costly for others. Pick the skills you want to keep strong, and regularly do that work yourself, or with the agent only reviewing. Fluency includes knowing when *not* to delegate.

<TryIt title="Write Your Personal Shipping Checklist">

Write a short checklist you'll run before committing agent-assisted code. Start with these and adapt:

1. I read the full diff, not just the summary.
2. I ran the key check myself.
3. No tests were deleted or weakened without a reason I agree with.
4. No secrets, debug code, or unrelated changes are included.
5. I pass the explain-it test for the risky parts.
6. Attribution and disclosure match my team's or project's rules.

Put it somewhere you'll see it, such as your personal `~/.claude/CLAUDE.md`, a PR template, or a sticky note.

</TryIt>
