## The Limits of a Frontend-Only App

The user story hasn't changed since Module 2. What changes is the question behind it: the app works — so why add more moving parts?

Because a frontend alone has four hard limits:

1. **Limited data handling.** React Native is built for interfaces, not for storing and querying large datasets. A real movie catalog has tens of thousands of entries with cast, plot, ratings, and more.
2. **No shared, persistent data.** Data that lives on the device disappears when the app is uninstalled, isn't there when the user switches phones, and can't be updated for everyone at once.
3. **Security.** As Module 2 showed, nothing on the client can be trusted or kept secret. Validation, access control, and credentials need a place the user can't tamper with.
4. **Tangled concerns.** Mixing display logic, business rules, and data access in one codebase makes every change risky.

The fix is the classic shape of web and mobile systems: **full-stack** development, where you build both the interface (frontend) and the server-side logic and storage behind it (backend).

- **Presentation tier** — the frontend. It displays data and collects input, and it is *untrusted*.
- **Application tier** — the backend, or API server. It applies business rules (filtering, validation, permissions), holds secrets, and decides what each request is allowed to do. In this app it's built with **Express**, a minimal web framework for **Node.js** (JavaScript running on a server).
- **Data tier** — the database. It stores data durably and answers queries. Clients never talk to it directly; only the application tier does.

The value of this split is **separation of concerns**: each tier can be developed, tested, secured, and scaled independently. You can redesign the app's screens without touching the database, or move the database without changing the screens.

The stack in this module has a common nickname — **MERN**: **M**ongoDB, **E**xpress, **R**eact (here, React Native), and **N**ode.js.

## The Data Tier: SQL vs. NoSQL

A **database** is an organized collection of data stored and accessed electronically. There are two broad families:

| | SQL (relational) | NoSQL (document, key-value, graph, ...) |
|---|---|---|
| **Shape** | Tables of rows and columns with a fixed schema | Flexible structures; documents can differ |
| **Relationships** | Joins across tables | Often embedded inside one document |
| **Schema changes** | Planned migrations | Add fields as you go |
| **Strengths** | Strong consistency, complex queries, transactions | Flexible data, horizontal scaling, natural fit for JSON |
| **Examples** | PostgreSQL, MySQL | MongoDB, DynamoDB, Redis |

Neither is "better." The choice depends on the data's shape and how it's queried.

### MongoDB: documents and collections

**MongoDB** is a document database. A **document** is a JSON-like record (stored in a binary form called BSON), and related documents are grouped in a **collection** — roughly analogous to a table, but without a fixed schema. A movie document looks like this:

```json
{
  "title": "Inception",
  "year": 2010,
  "genres": ["Action", "Adventure", "Sci-Fi"],
  "cast": ["Leonardo DiCaprio", "Elliot Page"],
  "imdb": { "rating": 8.8, "votes": 2070468 }
}
```

Lists (genres, cast) and nested objects (the IMDb rating) live right inside the record — no extra tables or joins. Movies are a natural fit: some have awards, some don't; some list writers, some don't. The app in this course uses MongoDB's public **sample movie dataset**, a collection of thousands of real movie documents with titles, genres, cast, plots, and ratings. Its richness is what makes recommendations and chat possible later.

### Managed databases

**MongoDB Atlas** is MongoDB offered as a managed cloud service — a PaaS in Module 1's terms, often called **DBaaS** (database as a service). You choose a cloud provider and region; Atlas runs the servers, replication, backups, and upgrades. A **cluster** is the group of database servers holding your data, and a free tier is enough for learning.

## Reaching the Database Safely

Two settings decide who can talk to an Atlas cluster.

**1. Database users.** Every connection authenticates with a username and password. Give each application its own user with only the permissions it needs — read-only if it only reads. This is the **principle of least privilege**.

**2. Network access.** Atlas also keeps an **IP access list**: only connections from listed IP addresses are accepted, even with a valid password. That's **defense in depth** — two independent locks.

The application finds the cluster through a **connection string**:

```
mongodb+srv://<user>:<password>@<cluster-host>/<database>?retryWrites=true
```

The `mongodb+srv` scheme tells the driver to look up the cluster's servers via DNS. Notice that this one string contains a password — it is a **secret**, and the next lesson shows where secrets belong.

<Pitfall title="Allowing Access from Anywhere (0.0.0.0/0)">

**Common mistake:** adding `0.0.0.0/0` to the network access list because a cloud dev environment's IP address keeps changing.

`0.0.0.0/0` means *every IPv4 address on the internet*. It removes the network lock entirely and leaves the password as your only protection. Internet-wide scanners constantly probe for exposed databases, and weak or leaked credentials have caused countless breaches. It's tolerable for a throwaway sandbox with sample data; for anything real, allow only your server's fixed address, or use private networking between your servers and the database.

</Pitfall>
