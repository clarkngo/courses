## "It's Running, So Why Can't the Phone Reach It?"

The API answers in a desktop browser at `http://<public-ip>:3000/movies`, yet the mobile app's request fails. Three separate networking facts explain it.

### 1. Private addresses and NAT

Most devices don't have a public internet address. Your laptop, your phone on Wi-Fi, and a container in a dev workspace all have **private IP addresses** (ranges like `10.x.x.x` or `192.168.x.x`) that only mean something inside their local network. A router performs **NAT** (network address translation): it rewrites outgoing traffic to use one shared public address and tracks the replies.

NAT has a key consequence: **outbound connections work; unsolicited inbound connections don't.** Your phone can reach a server, but nothing on the internet can start a connection to a service sitting behind your home router or inside a dev container — unless something is explicitly forwarded.

### 2. Ports and firewalls

A connection targets an address *and* a port. Common services use well-known ports — 80 for HTTP, 443 for HTTPS. Uncommon ports like 3000 may be blocked by mobile carriers, corporate and campus networks, or the server's own firewall (the security group from the last lesson). A URL that works from one network can fail from another.

### 3. HTTPS requirements on mobile

**HTTP** sends everything in plain text: anyone on the path — a café Wi-Fi operator, a compromised router — can read or alter it. **HTTPS** is HTTP over **TLS** (Transport Layer Security), which provides:

- **Encryption** — eavesdroppers see only scrambled data.
- **Integrity** — tampering is detected.
- **Server authentication** — a **certificate** issued by a trusted certificate authority proves the server really owns the domain name.

Because of this, modern mobile platforms **block plain-HTTP requests by default** (iOS through App Transport Security, Android by disabling cleartext traffic for current app targets). Developers can add exceptions, but the platforms are steering everyone toward HTTPS — and a bare IP address can't easily get a publicly trusted certificate.

1. A small **agent** on the server opens an **outbound** connection to the provider. Outbound traffic passes NAT and most firewalls.
2. The provider assigns a **public HTTPS URL** on port 443, covered by its own trusted certificate.
3. When the phone calls that URL, the provider **terminates TLS**, then sends the request back down the agent's existing connection to `localhost:3000`.

From the phone's point of view it's talking to a normal, trusted HTTPS endpoint. That's why the deploy job in the last lesson installs the agent, authenticates it with an **auth token** (stored as a pipeline secret), starts the tunnel, and prints the public URL — which then becomes the frontend's `API_URL`.

| Problem | How the tunnel helps | Production alternative |
|---|---|---|
| Server behind NAT or firewall | Agent connects outbound | A public load balancer or reverse proxy |
| Unusual port blocked | Public URL uses 443 | Serve on 443 directly |
| Phone requires HTTPS | Provider's certificate | Your own domain with a free certificate (e.g. Let's Encrypt) |
| URL changes often | Paid plans offer fixed domains | Stable DNS name you control |

## What You Trade Away

Tunnels are excellent for development, demos, and webhook testing. Know the trade-offs before relying on one:

- **A third party sits in the middle.** TLS ends at the provider, so it can see the decrypted traffic. Fine for a public movie list; a real concern for personal or regulated data.
- **Dependency and limits.** Free tiers rate-limit traffic, and URLs can change on restart — every change means updating the app's configuration.
- **It routes around your perimeter.** The same property that makes tunnels convenient — "bypassing" NAT and firewalls by connecting outward — is why security teams watch for them. An unapproved tunnel on a company laptop can expose internal systems to the internet without anyone in IT knowing.

<Pitfall title="Assuming HTTPS Means the Whole Path Is Private">

**Common mistake:** believing that because the phone shows an HTTPS URL, the traffic is encrypted all the way to the API.

With a tunnel, TLS covers phone → provider; the provider → agent leg travels inside the tunnel's own encrypted connection, but the provider itself handles plain requests. With a load balancer, TLS often ends at the balancer and continues as plain HTTP inside the cloud network. Always ask **where TLS terminates** and who can see traffic after that point.

</Pitfall>
